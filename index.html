What Version 2.1 adds

Decision and objective interfaces

  • structured perceived decision state P_i(t);
  • adjacent actor objective interface O_i(t);
  • descriptive Objective Responsiveness;
  • bounded objective-directed discovery; and
  • objective lifecycle dependency and bounded re-entry.

Evidence, history, and reconstruction

  • authority/applicability/permitted-use information governance;
  • disposition-preserving retrieval and temporal provenance;
  • Transfer History as a role-distinct event substrate;
  • Replay Sufficiency; and
  • Transition-Relevant State Sufficiency contracts.
Objectives do not become hidden utility, selection authority, adequacy overrides, viability conditions, or sources of nonexistent future capability. Capability-development objectives can influence only authorized channels; desired capability becomes current Productive Power only after a realized and evidenced capability/state transition.

Host/runtime boundary

The runtime owns

  • the implemented common PV-PP decision and governance architecture;
  • registered and governed represented structure;
  • implemented candidate/completeness, constraints, adequacy, and selection surfaces;
  • execution licensing and ε authority boundaries;
  • governed invalidation and re-entry; and
  • the Version 2.1 validation/governance interfaces actually present in v0.141.

The host/application owns

  • authoritative actual state and domain/world mechanics;
  • semantic completeness of domain-specific transition-relevant state;
  • application-specific measurements and objective content;
  • external persistence, instrumentation, and enforcement mechanisms;
  • environmental realization; and
  • the authoritative Layer-1 state transition.

Runtime selection, licensing, or a successful native call does not itself prove that the authoritative external world reached the intended successor state.

Runtime V2.1 execution boundary

Runtime V2.1 preserves authority-bound synchronous native call-through. Consequential invocation through the runtime must derive from the applicable runtime-issued governance lineage rather than from host-created authority-looking objects.

The frozen v0.141 runtime remains synchronous. It has no asynchronous sensing, external instrumentation hooks, or autonomous in-flight environment-change detection. Applications may supply instrumentation and updated state/evidence around the runtime, but those capabilities must not be attributed to v0.141 itself.

PV-PP runtime governance also does not replace operating-system security, IAM, network enforcement, sandboxing, or other conventional controls required by the deployment environment.

Repository organization

The three preserved runtime generations are kept side by side:

PV-PP-Runtime-API/ ├── runtime-v1/ # frozen v0.70 historical generation ├── runtime-v2/ # frozen v0.131 prior successor └── runtime-v2.1/ # current frozen v0.141 Version 2.1 successor

Development builds remain engineering history rather than additional top-level supported generations. Runtime-specific source, tests, examples, benchmarks, release records, and documentation should remain with the generation they describe.

About PV-PP

Productive Value–Productive Power (PV-PP) is a productive-system and decision framework centered on Productive Value, Productive Power, actual and perceived state, actor objectives, viability, recovery, governance, candidate construction, selection, consequential execution, and authoritative state transition.

This site concerns the Runtime API specifically. It does not reproduce the complete theoretical, mathematical, benchmark, proof, or research record of the PV-PP framework.
